The boring OLX scraper that covers 24 countries — and why I kept it to one file

One input, 24 domains, one flat price. How a single-file scraper handles OLX without pretending every country behaves the same.

Prime Sieve · Aug 22, 2026 · 6 min

OLX looks like one site. It is not. It is two dozen sites that share a logo.

Indonesia is olx.co.id. Poland is olx.pl. Brazil is olx.com.br. Then there is Ukraine, India, Portugal, Romania, Kazakhstan, Uzbekistan, Pakistan, South Africa, Nigeria, Kenya, Egypt, Lebanon, Philippines, Colombia, Argentina, Peru, Ecuador, Guatemala, Azerbaijan, Morocco. Same brand. Different domains. Different anti-bot setups. Different ways to break.

Most scrapers pick one country and call it done. I kept forking that idea and got tired of it. So I put all 24 behind one input.

It is live on Apify: primesieve/olx-global-scraper. One file. No browser. Here is the boring part.

The pitch in one input

{
  "country": "id",
  "keywords": ["iphone 13"],
  "maxResults": 50,
  "maxPages": 3
}

Change country to "pl" or "br" or "za" — same schema out:

{
  "listingId": "123456789",
  "title": "iPhone 13 128GB mulus",
  "price": 6500000,
  "priceText": "Rp 6.500.000",
  "currency": "IDR",
  "city": "Jakarta Selatan",
  "location": "Tebet, Jakarta Selatan, DKI Jakarta",
  "images": ["https://...jpg"],
  "thumbnailUrl": "https://...jpg",
  "listingUrl": "https://www.olx.co.id/item/123456789",
  "country": "id"
}

Title, price as a number plus display text, currency, location, images, URL. No seller PII beyond what the listing shows. The point is you can point the same pipeline at Warsaw or Jakarta and not rewrite the parser.

That uniformity was the hard part. Not the scraping. The decision to keep one schema honest across 24 messy domains.

I curl the target before I write the scraper

Same line I put in every post because it is the only workflow that has not wasted my time:

I curl the target before I write the scraper. If a JSON endpoint answers, I never open a browser. Browsers are expensive. Boring code is cheap.

Indonesia answered cleanly. No proxy, structured response, fast. The other 23 do not. They sit behind CloudFront or Cloudflare and return 403 without a residential proxy. You can test this in one curl — Jakarta returns 200, Warsaw returns a wall. That one check decided the whole architecture.

So the scraper has two paths and I am honest about it in the README. One path that runs clean without a proxy. One path that requires one and fails fast if you omit it. Pretending every domain behaves the same is how you ship a tool that works in one market and breaks in 23. Two paths is not clever. It is truthful.

I will not paste endpoints or selectors here. They change. You have seen this before if you maintain scrapers: the selector that works on Tuesday breaks on Thursday because someone renamed a data-cy attribute. The contract that matters to you is input and output. What is inside the parse ladder is my maintenance burden, not your integration point. That is deliberate — no secret sauce spilled, no brittle tutorial to copy-paste into a broken fork next month.

The stack is boring on purpose

apify + fetch + cheerio

Apify SDK for input, dataset, and pay-per-event. Native fetch for HTTP. cheerio for the HTML path. Undici ProxyAgent when a proxy is configured. Node 20, 512 MB, 600 seconds. One file in src/main.js.

People ask why not Playwright. The answer is cost. A run that fetches 50 listings should not spin up a browser that eats 2 GB. If a JSON endpoint answers, fetch wins. If HTML answers, a fetch plus a parser wins until the site proves you need more. Most OLX search pages answer to a plain fetch with a desktop user-agent and a residential proxy. Save the browser budget for the sites that truly require it.

Boring code never wakes you at 2am. That line is not a joke. I have a notes file of failure modes — one line each, what broke, what changed, what I would do differently. Most are boring. A few become README warnings that save users a headache. Every retired tool gets a one-line obituary in its README. A tool that never died was never maintained.

Why flat pricing

$0.003 per product. PAY_PER_EVENT. One event is one listing pushed to the dataset. 1,000 listings is $3. 10,000 is $30. No tiers. No credits. No "contact sales."

I priced this flat because I priced my first actor wrong. My Tokopedia scraper story is the same lesson: the leader was a third of my price with years of reviews. I learned to check the store before I check my code. Tiered per-1k pricing with volume breaks works for enterprise contracts. It is bad for a solo dev pulling 2,000 rows for a price tracker who wants a predictable number to put in a spreadsheet.

Indonesia stays the default so existing users of my single-country OLX actor see no billing change. Other countries add the proxy cost from Apify (residential usage) but the product charge itself stays $0.003 everywhere. You can quote it to your boss without a table.

What actually broke while building it

Five small lessons. None is impressive. All would have cost a user a corrupted dataset if I skipped them.

1. Validate country early. A typo in country should fail in second one, not after three pages of empty fetches. The actor throws on unknown codes and prints the allowed list. Small thing. Saves a whole run.

2. Fail loud on zero cards. If a proxied fetch returns HTML with no listing cards, that is not "zero results." It is a WAF or a layout change. The actor logs the HTTP status, warns, and stops that keyword instead of pushing nothing and pretending it succeeded. Silent zero-row runs corrupt datasets. I added this after my government-agency scraper silently succeeded with zero records on day three because a selector got too strict. Now zero expected is an error, not a success.

3. Deduplicate by URL. Paging overlaps. Sponsored placements repeat. A Set on listingUrl costs nothing and saves you cleaning it later.

4. Keep the input small. Five fields. Two enums. No 15-param form. Apify's input schema needs an editor type on every property (stringList, number, select) or the build fails. I learned that on the Tokopedia actor the hard way — one missing editor line, one failed build.

5. Sleep between pages. 500ms on the clean path, 900ms on the HTML path. Not because the code is slow. Because being polite is cheaper than being blocked. Rate-limit backoff is not a feature. It is manners.

The honest part

This is on a free-tier Apify account. Zero users today. It will not make me rich overnight. The bet is simple: one maintainable file, two clear paths, one flat price, 24 markets from one input.
